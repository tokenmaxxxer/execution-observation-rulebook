# qa-agent-rulebook — 설계 기록

*[English](design.md)*

*2026-07-24. v0.1 스캐폴딩 전에 논의된 설계 그대로 — 이후 기여자가 읽을 수
있는 근거(rationale)로 보존.*

## 전제

대상 프로젝트에 대해 Claude Code 세션이 **QA로서 동작하게** 만드는 스택.
의도적으로 기능 우선(function-first): 라인업은 자매 coding 스택의
생성/검증 테제가 아니라 QA 엔지니어가 실제로 하는 일에서 도출했다.
[coding-agent-rulebook](https://github.com/tokenmaxxxer/coding-agent-rulebook)
에서 물려받은 것은 패키징뿐이다: 마켓플레이스 구조, 플러그인당 디렉토리
하나, 얇은 셸 스크립트 훅, 플러그인별 kill switch("off means off" —
비어있지 않은 값 처리 교훈 포함), `*-env` 의존성 번들, 정직한
"Unbenchmarked as of vX" 표기.

## QA 사이클 → 플러그인 매핑

실무 QA는 다섯 블록으로 분해된다: **설계 → 실행 → 리포트 → 회귀 → 사인오프**.

| 블록 | 플러그인 | v0.1? |
|---|---|---|
| 프로젝트 온보딩 | intake | ✅ |
| 실행 | testrun | ✅ |
| 리포트 | bugreport | ✅ |
| 테스트 설계 | testplan | 로드맵 |
| 회귀 | regress | 로드맵 |
| 사인오프 | signoff | 로드맵 |

v0.1은 자립 가능한 최소 스택이다: *프로젝트를 프로파일링하고, 제품을 돌리고,
깨지는 것을 발행한다*. testrun은 의도적으로 플랜 없이도 동작하게(애드혹
스모크) 설계해서 testplan이 나중에 v0.1을 막지 않고 얹힐 수 있다.

무게중심이 coding 스택과 다르다: 그쪽은 거의 전부 `UserPromptSubmit` 조향
산문이었지만, QA는 절차적 작업이라 무게가 **command/skill**(실행 가능한
절차)에 실리고 directive는 아래 두 불변식만 얇게 남는다.

## 두 불변식

1. **Verdict에는 실행이 필요하고, 증거가 붙는다.** QA 에이전트는 실제로
   돌려보지 않은 것에 pass/fail을 주장할 수 없다. 모든 verdict는
   커맨드+출력, 스크린샷, 로그를 인용한다. 코드 읽기는 노트를 낳을 뿐이다.
2. **고치지 말고 리포트한다.** QA 세션은 제품 코드를 수정하지 않는다.
   발견은 트래커 이슈나 run record가 된다. (v0.1은 directive로 강제;
   드리프트가 관찰되면 제품 코드 수정을 거부하는 `PreToolUse` 게이트가
   자연스러운 기계적 업그레이드다.)

## intake: 왜 별도 플러그인인가

이슈 발행처·템플릿·라벨은 bugreport만의 것이 아니다: testrun은 기동법과
환경이, regress는 테스트 스택 컨벤션이 필요하다. 그래서 프로젝트 지식은 한
번 발견되고(`/qa-init`), 커밋되는 파일 하나(`qa/intake.md`)로 동결되고,
전원이 읽는다. 에이전트가 발견할 수 없는 필드(별도 트래커 repo, 스테이징
URL, 테스트 계정)는 추측하지 않고 묻는다. 시크릿은 env var *이름*만 기록.

`/qa-init --check`는 닥터: 프로파일 존재, `gh` 인증, 이슈 repo 접근, 기동
커맨드 존재, 명명된 env var 세팅 여부.

## 회사 단위 배포: 3층 모델

확인된 메커니즘: 프로젝트에 커밋된 `.claude/settings.json`이
`extraKnownMarketplaces` + `enabledPlugins`를 선언할 수 있고, 선언된
플러그인은 세션 시작 시 자동 설치된다. 프라이빗 GitHub 마켓플레이스는 일반
git 인증으로 동작한다(백그라운드 자동 업데이트는 `gh auth setup-git` 또는
SSH 필요). 레포 스코프 플러그인은 `claude -p` 헤드리스 세션에서도
로드된다(`--bare` 제외). 마켓플레이스의 `version` 필드로 버전 고정이
가능하고, 브랜치 두 개로 stable/latest 채널 분리도 가능하다.

1. **회사층 — 이 마켓플레이스 레포.** 회사 공통 표준은 플러그인 안에
   산다(표준 버그 양식 폴백, severity 폴백 체계, 증거 규칙). 표준 변경은
   여기에 PR로 이뤄지고 플러그인 업데이트로 전파된다.
2. **프로젝트층 — 대상 레포마다 커밋되는 파일 2개.**
   `.claude/settings.json`(레포를 여는 모든 사용자에게 자동 설치, CI 포함 —
   경계는 팀 소속이 아니라 레포 접근 권한 + 폴더 trust)과
   `qa/intake.md`(공유 프로파일 하나: 전원 같은 트래커, 같은 템플릿, 같은
   라벨, 같은 기동법).
3. **개인층 — 시크릿과 kill switch.** 프로파일이 이름만 적어둔 env var의
   값, 그리고 `QA_*_OFF` 스위치.

우선순위: 플러그인 내장 회사 표준 < intake 프로파일 < 사용자의 세션 지시.

미해결 항목:
- 레포 설정발 최초 자동 설치에 trust 프롬프트가 뜨는지는 문서화되어 있지
  않다 — 한 번 실측해서 온보딩 문서에 기록할 것.
- `install.sh`(유저 스코프 경로)는 v0.1에서 의도적으로 스킵: 회사 경로가
  레포 스코프 설정이고, 개인은 `/plugin`으로 수동 설치 가능. 독립 QA 세션
  워크플로우가 실제로 생기면 추가.

## `qa/` 계약

스택의 모든 상태는 대상 레포에 커밋되어 산다 — 프로파일, 플랜, run record,
증거. 중단된 세션은 디스크에서 재개되고, 모든 사용자가 하나의 상태를
공유하며, CI도 같은 기록을 읽고 쓴다. run record는 실패를 그것이 된 이슈와
연결한다(아니면 `UNFILED(<이유>)`) — 나중에 signoff 플러그인이 당길 실이
바로 이것이다.

## 로드맵 노트

- **testplan**: 스펙/PR → 경계값, 동등분할, 네거티브 경로, 상태전이 기반
  케이스 도출; signoff가 실행 기록과 대조할 요구사항↔케이스 추적성.
- **regress**: 확정된 버그마다 → 프로파일의 `tests:` 스택으로 "그 버그를
  잡았을" 자동화 테스트 작성; 실행 간 flaky 탐지; 회귀 시 `git bisect`.
- **signoff**: 플랜 대비 실행 요약 — 실행/통과/실패/블록, 커버리지 구멍,
  열린 블로커. 인간을 위한 판단 *재료*이지 출시 가부 verdict가 아니다.
- **CI**: 같은 플러그인을 쓰는 헤드리스 세션으로 예약 스모크 — 원리상 지금도
  동작; v0.1이 안정되면 제품화.
